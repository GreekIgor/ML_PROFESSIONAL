# Прогноз времени выполнения производственного задания

Учебный проект (ML-Professional), построенный на доменной модели реального
ERP-проекта для упаковочного производства (ASPMK-like): заказы → изделия →
маршрутные листы → производственные задания → назначения рабочим.

## Постановка ML-задачи

**Тип задачи:** регрессия.

**Цель:** по параметрам производственного задания предсказать **фактическое
время выполнения** (`actual_minutes`) — сколько реально уйдёт на операцию,
а не сколько заложено по норме (`norm_minutes`).

**Зачем это нужно бизнесу:** нормо-время в ERP — плановая величина, посчитанная
по регламенту. Она не учитывает, что конкретный рабочий работает быстрее/медленнее
нормы, что ночная смена и понедельник/пятница дают просадку эффективности, что
рабочего иногда ставят не по профилю специальности. Модель, предсказывающая
факт, даёт более точную оценку `end_date` задания при планировании загрузки цеха.

**Целевая переменная:** `actual_minutes` — обучение идёт на `log1p(actual_minutes)`,
чтобы сгладить сильный разброс масштаба заданий (от 5 до тысяч минут), а метрики
считаются после обратного преобразования (`expm1`), то есть в исходных минутах.

**Метрики качества:** `MAE` (в минутах — интерпретируема для бизнеса: "модель
ошибается в среднем на N минут") и `R²` (доля объяснённой дисперсии).

## Данные

**Расположение:** [data/production_tasks.csv](data/production_tasks.csv) —
12 000 строк, генерируется скриптом [generate_dataset.py](generate_dataset.py)
(`python generate_dataset.py`).

Датасет **синтетический**, но построен так, чтобы воспроизводить реальные
зависимости из прод-системы: у каждого рабочего есть скрытый навык
(`_skill_factor`, не подаётся модели напрямую), у изделия — скрытая сложность
(`_complexity`); фактическое время — функция от нормы, навыка рабочего,
несоответствия специальности цеху, ночной смены, дня недели (понедельник/пятница)
и перегрузки по объёму, плюс случайный шум. Модель должна выучить эти
зависимости по наблюдаемым признакам, не видя скрытых величин напрямую.

Ключевые столбцы: `task_date`, `weekday`, `shift`, `workshop`, `worker_id`,
`worker_speciality`, `required_speciality`, `speciality_mismatch`,
`worker_experience_years` (3% пропусков — имитация реального прода),
`product_id`, `product_group`, `quantity`, `norm_minutes`, `actual_minutes`.

## Пайплайн предобработки данных

Реализован как `sklearn.pipeline.Pipeline` + `ColumnTransformer`
([production_time_prediction.ipynb](production_time_prediction.ipynb), разделы 3–4):

```
ColumnTransformer([
    ("num", StandardScaler(),      numeric_cols),
    ("cat", OneHotEncoder(handle_unknown="ignore"), categorical_cols),
])
```

- **Числовые признаки** (`norm_minutes`, `quantity`, `quantity_per_norm_minute`,
  `speciality_mismatch`, `worker_experience_years`, `is_weekend_adjacent`,
  `is_night`) — `StandardScaler`. Нужен для моделей, чувствительных к масштабу
  (Linear Regression, SVR); деревьям и бустингу не мешает, поэтому единый
  препроцессор используется во всех пайплайнах без потери качества у ансамблей.
- **Категориальные признаки** (`workshop`, `product_group`, `worker_speciality`)
  — `OneHotEncoder(handle_unknown="ignore")`. `handle_unknown="ignore"` — чтобы
  категория, не встреченная на train (например, новый цех), не ронял инференс,
  а просто давала нулевой вектор.
- Пропуски в `worker_experience_years` заполняются медианой по train до сборки
  `X`/`y` (простое и устойчивое к выбросам решение для учебного пайплайна).
- Препроцессор обёрнут в `Pipeline` вместе с моделью — это гарантирует, что
  скейлер/энкодер обучаются **только на train** и не подсматривают в
  validation/test (иначе была бы утечка данных через статистики скейлера).

## Feature engineering

Реализовано в разделе 3 ноутбука. Осознанно взяты только признаки, которые в
реальном проекте вычисляются из `task_assignments`/`production_tasks` **без
дополнительного сбора данных** — то есть пайплайн можно сразу перенести на
прод-выгрузку:

| Признак | Как считается | Почему нужен |
|---|---|---|
| `is_weekend_adjacent` | `weekday ∈ {Пн, Пт}` | эффект "разгона"/усталости в начале и конце недели, заложен прямо в генератор данных |
| `is_night` | `shift == "night"` | ночная смена стабильно даёт просадку эффективности |
| `quantity_per_norm_minute` | `quantity / norm_minutes` | интенсивность операции — нормирует объём партии на уже заложенное нормо-время, чтобы модель видела не сырой объём, а "плотность" задания |
| `speciality_mismatch` | уже есть в сырых данных | ключевой сигнал: рабочего поставили не по профилю — самый сильный множитель замедления в данных |
| `log1p(actual_minutes)` | таргет-трансформация | стабилизирует дисперсию таргета, который отличается на порядки между мелкими и крупными заданиями |

Признаки `worker_id`, `product_id`, `task_id` намеренно **не используются** —
это идентификаторы, а не обобщаемые характеристики; их прямое использование
дало бы false-положительное качество на train/val (утечка через ID) без
пользы на новых рабочих/изделиях, которых не было в обучении.

## Модели и их сравнение

Раздел 4–7 ноутбука сравнивает 6 моделей на одной и той же схеме признаков и
препроцессинге, от простого к сложному — baseline → интерпретируемая модель →
ансамбли → метод, ориентированный на маленькую выборку:

1. **Linear Regression** — baseline.
2. **Decision Tree** (`max_depth=6, min_samples_leaf=20`) — ценен не точностью,
   а интерпретируемостью (правила можно показать мастеру цеха).
3. **Random Forest** (`n_estimators=300, max_depth=10`).
4. **Gradient Boosting** (sklearn, `n_estimators=300, max_depth=3, learning_rate=0.05`).
5. **CatBoost** (`iterations=500, depth=6, learning_rate=0.05, loss_function="MAE"`) —
   работает с категориальными признаками нативно, без OneHot.
6. **SVR** (`kernel="rbf"`) — обучается на подвыборке из 2000 строк, так как
   плохо масштабируется на десятки тысяч строк; ориентир для сценария "мало
   исторических данных" (новый цех/линия).

### Выбранная модель

**Gradient Boosting (sklearn)** — лучшая по MAE на validation среди всех
моделей, при этом с наименьшим разрывом train/val среди ансамблей (см. ниже).
CatBoost показывает практически идентичный результат (разница в пределах шума
random_state) — оба варианта пригодны, GB выбран как чуть более точный на этом
прогоне и не требующий внешней зависимости.

## Метрики обучения модели

Данные разбиваются на **три независимые выборки** (раздел 3.1 ноутбука):

- **train (60%, 7200 строк)** — обучение моделей;
- **validation (20%, 2400 строк)** — сравнение моделей и диагностика
  переобучения; используется многократно по ходу работы;
- **test (20%, 2400 строк)** — используется **один раз**, в самом конце,
  только для лучшей модели — чтобы получить честную несмещённую оценку.

Метрики (train → validation), из фактического прогона ноутбука:

| Модель | train MAE | train R² | val MAE | val R² |
|---|---|---|---|---|
| Linear Regression | 218.2 | 0.669 | 215.8 | 0.700 |
| Decision Tree | 126.3 | 0.898 | 129.6 | 0.887 |
| SVR (2000 строк) | 71.2 | 0.969 | 136.6 | 0.866 |
| Random Forest | 88.4 | 0.952 | 112.7 | 0.916 |
| CatBoost | 93.7 | 0.943 | 99.7 | 0.935 |
| **Gradient Boosting** | **95.0** | **0.943** | **98.9** | **0.936** |

**Финальная проверка лучшей модели (Gradient Boosting) на test:**

```
MAE = 98.2 мин, R² = 0.941
(на validation было: MAE = 98.9 мин, R² = 0.936)
```

Метрика на test практически совпадает с validation → выбор модели/гиперпараметров
не был подогнан под validation, оценка на новых данных надёжна.

## Кривая обучения (learning curve)

Раздел 9 ноутбука строит `sklearn.model_selection.learning_curve` для лучшей по
validation модели: MAE на train и на кросс-валидации (`cv=5`) в зависимости от
доли обучающей выборки (10% → 100%). Используется, чтобы понять:

- сходятся ли кривые (модель близка к потолку качества при текущем наборе
  признаков — расширение данных даст мало) или продолжают расходиться (нужно
  больше данных или сильнее регуляризовать модель);
- на каком объёме данных train- и CV-метрика выходят на плато.

## Борьба с переобучением

Основной инструмент диагностики — таблица `train_MAE` / `val_MAE` и разрыв
между ними (`gap_MAE`, `gap_R2`) для каждой модели (раздел 9):

- **Linear Regression** — маленький разрыв, но и train, и val метрика слабые →
  **недообучение** (модель слишком простая для нелинейных взаимодействий вроде
  "несоответствие специальности × ночная смена").
- **SVR** и в меньшей степени **Random Forest** — заметный разрыв train/val
  (SVR: 71 → 137 мин) → **переобучение**, ожидаемо: SVR обучен всего на 2000
  строках, RF — глубокие деревья (`max_depth=10`) без сильной регуляризации.
- **Gradient Boosting / CatBoost** — наименьший разрыв среди моделей с хорошим
  качеством → лучший баланс bias/variance на этих данных.

Конкретные меры, применённые/заложенные в пайплайне для борьбы с переобучением:

1. **Отдельная validation-выборка** — все решения о выборе модели принимаются
   по val, а не по test, чтобы не переобучиться на тестовых данных при выборе.
2. **Регуляризация гиперпараметрами**: `max_depth`, `min_samples_leaf` у дерева
   и леса, `n_estimators`/`learning_rate`/`max_depth` у бустинга — специально
   ограничены (например, `max_depth=3` у sklearn GB) вместо "чем больше, тем
   лучше".
3. **Кросс-валидация в learning curve** (`cv=5`) — метрика на кривой обучения
   усреднена по 5 фолдам, а не по одному разбиению, что снижает шум оценки.
4. **Тест используется один раз** — только для итоговой проверки, что
   предотвращает "подгонку под тест" через многократный подбор по нему.
5. **Никаких ID-признаков** (`worker_id`, `product_id`) в модели — иначе
   модель могла бы запомнить конкретных рабочих/изделия из train, что выглядело
   бы как отличное качество на train/val, но не обобщалось бы на новых
   рабочих/изделия в проде.

## Как воспроизвести

```bash
python generate_dataset.py      # пересоздаёт data/production_tasks.csv
python build_notebook.py        # пересобирает .ipynb из исходников ячеек
jupyter nbconvert --to notebook --execute --inplace production_time_prediction.ipynb
```

`build_notebook.py` — единственный источник правды для содержимого ноутбука;
редактировать `.ipynb` вручную не нужно, изменения вносятся в `build_notebook.py`
и пересобираются командой выше.
